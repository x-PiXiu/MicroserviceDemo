# 五子棋游戏业务逻辑流程图

```mermaid
sequenceDiagram
    participant C1 as 客户端A
    participant C2 as 客户端B  
    participant API as HTTP API
    participant WS as WebSocket
    participant Room as GomokuRoom
    participant Logic as GomokuLogic
    participant EventLoop as EventLoop

    Note over C1,EventLoop: 🔧 实际业务流程（与预期的差别）

    %% 1. 房间创建和加入
    C1->>API: POST /api/gomoku/rooms (创建房间)
    API->>Room: createGomokuRoom()
    API-->>C1: 201 房间创建成功 + roomId
    
    C2->>API: POST /api/gomoku/rooms/{id}/join (加入房间)
    API->>Room: addPlayer()
    API-->>C2: 200 加入成功

    %% 2. WebSocket连接（认证在连接后）
    C1->>WS: WebSocket连接
    C1->>WS: {"type": "auth", "token": "xxx"}
    WS-->>C1: 认证成功
    
    C2->>WS: WebSocket连接  
    C2->>WS: {"type": "auth", "token": "xxx"}
    WS-->>C2: 认证成功

    %% 3. 🔧 差别1：join_room通过WebSocket或HTTP都可以
    C1->>WS: {"type": "join_room", "roomId": "xxx"}
    C2->>WS: {"type": "join_room", "roomId": "xxx"}
    WS->>Room: handleWebSocketJoin()
    
    %% 4. 开始游戏
    C1->>API: POST /api/gomoku/rooms/{id}/start 
    API->>Room: startGame()
    Room->>Logic: startGame()
    
    %% 🔧 差别2：启动定时器主循环而不是简单的游戏循环
    Logic->>EventLoop: runEvery(100ms, tick())
    EventLoop-->>Logic: 定时器ID
    
    %% 🔧 差别3：立即广播初始状态
    Logic->>Room: notifyStateUpdate()
    Room->>WS: broadcast("game_state", initialState)
    WS-->>C1: game_state消息
    WS-->>C2: game_state消息

    %% 5. 游戏进行循环
    loop 游戏进行中
        %% 玩家落子
        C1->>WS: {"type": "place_piece", "position": {row, col}}
        WS->>Room: handlePlacePiece()
        Room->>Logic: placePiece()
        Logic-->>Room: 落子结果
        
        %% 🔧 差别4：多重广播机制
        Room->>WS: broadcast("move_result", result)
        Room->>WS: broadcast("game_state", newState)
        WS-->>C1: move_result + game_state
        WS-->>C2: move_result + game_state
        
        %% 🔧 差别5：定时器自动tick检查
        EventLoop->>Logic: tick() [每100ms]
        Logic->>Logic: checkGameEnd()
        Logic->>Logic: updateTimeControl()
        
        %% 🔧 差别6：时间控制广播
        Logic->>Room: onTimeUpdate()
        Room->>WS: broadcast("time_update", timeData)
        WS-->>C1: time_update
        WS-->>C2: time_update
    end
    
    %% 6. 游戏结束
    Logic->>Room: onGameEnd(winners)
    Room->>WS: broadcast("game_end", result)
    WS-->>C1: game_end
    WS-->>C2: game_end
    
    %% 🔧 差别7：自动停止定时器
    Logic->>EventLoop: cancelTimer(timer_id)
    EventLoop-->>Logic: 定时器已停止
```

## 🔧 主要差别说明

### 1. **房间加入方式**
- **预期**: 只通过HTTP API加入
- **实际**: 支持HTTP API和WebSocket两种方式

### 2. **游戏主循环机制**  
- **预期**: `tick() 每100ms检查游戏状态`
- **实际**: 基于EventLoop的定时器，`runEvery(100ms, tick())`

### 3. **消息广播类型**
- **预期**: 只有 `game_state`、`move_result`、`game_end`
- **实际**: 还包括 `time_update`、`chat`、`draw_offer` 等

### 4. **状态更新时机**
- **预期**: 定时检查后广播
- **实际**: 事件驱动 + 定时检查双重机制

### 5. **认证流程**
- **预期**: WebSocket连接时认证
- **实际**: 连接后发送auth消息认证

### 6. **观战者支持**
- **预期**: 未提及
- **实际**: 完整的观战者系统（join_spectator, leave_spectator）

### 7. **时间控制系统**
- **预期**: 未提及
- **实际**: 完整的时间控制（每步加时、超时判负）

## 💡 架构优势

1. **异步事件驱动**: 基于EventLoop的高性能架构
2. **多重通信**: HTTP + WebSocket 双通道
3. **实时响应**: 事件触发 + 定时检查
4. **完整功能**: 观战、时间控制、聊天、悔棋等
5. **状态一致性**: 多重广播确保状态同步
